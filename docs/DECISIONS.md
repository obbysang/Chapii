# DECISIONS — AgentVault (numbered log)

## Spec deviations (HACKATHON.md wins)
- D-001: Submission channel is POST https://nearhackathon.com/api/applications (or /#apply form), one-shot, not editable; changes via /request-changes. Spec §12.4 form fields map 1:1 (idea 20-2000 chars confirmed). Phase 9 uses these exact fields.
- D-002: 1-Click JWT optional (HACKATHON.md Q-006). Without JWT a ~0.2% (docs: +0.25%) unauthenticated fee applies. Executor must log fees; `ONECLICK_JWT` stays optional server-side only.
- D-003: HACKATHON.md Q-012 allows local-only demo but hosted is a plus; Q-017 AI screening scores reproducibility. Deployed demo + exact-output README are therefore treated as P0, not optional.

## [VERIFY] resolutions (checked 2026-11-08 against docs.near.org, docs.near-intents.org, crates.io, npm)

- V1 (near-sdk): CURRENT = near-sdk 5.30.1 (crates.io newest, 2026-11-05), near-workspaces 0.24.0 (Rust crates), near-contract-standards 5.30.1. Attributes confirmed: `#[near(contract_state)]`, `#[near]`, `store::IterableMap/LookupMap`, `Promise::new(..).add_access_key_allowance(pk, Allowance::limited(..), receiver, method)` + `delete_key(pk)`. Fallback: pin 5.30.1 exactly (Cargo.lock). Note: `#[near]` + `#[near(contract_state)]` replaced the old `#[near_bindgen]`/`#[init]`-only style; placeholder date in repo skeleton.
- V2 (signer_account_pk): `env::signer_account_pk()` returns the tx signer's public key (docs.rs near-sdk 5.30.1). When an agent signs **as the vault account** with a function-call key, `signer_account_pk` = that key and `predecessor == current_account_id`. Verified in Phase 0 experiment (see PROGRESS.md) — agent identity is the pk, not predecessor. Fallback (sub-account per agent) NOT needed.
- V3 (self key mgmt + zero keys): `Promise::add_access_key_allowance` / `delete_key` on `current_account_id` work from inside the contract (experiment (d) passed). An account with zero access keys is valid NEAR state (Locked mode target: after creation the vault has only the contract's self-added agent keys; owner deployer key removed or never added in Locked). Dev mode fallback if locked creation tx fails: keep deployer key, document.
- V4 (key restrictions): Function-call key with `receiver(current) + method("ping")` cannot attach deposit, cannot call other contracts, cannot call other methods — enforced at protocol level (experiment (c)); sandbox K1-K5 re-prove in Phase 2.
- V5 (batched create tx): CreateAccount+Transfer+DeployContract+FunctionCall(new) in one signed tx is standard NEAR batching; wallet-selector signTransactions supports sequential and batched actions, but support varies by wallet. Fallback (spec): sequential txs with progress UI — implement batched first, sequential fallback both paths (all three batched + sequential compatible).
- V6 (wallet): `@near-wallet-selector/core` latest 10.1.4 (stable; beta 10.0.0-beta.1, next 4.0.0); `@near-wallet-selector/modal-ui` 10.1.4. No `@near-js/wallet-selector` package. NEP-413 via `near api message sign` / `@near-js/signers` — use wallet-selector v10 + documented NEP-413 flow in Phase 6. Pin 10.1.4.
- V7 (near-api-js): `near-api-js` 7.4.0 now re-exports `@near-js/*` (accounts/transactions/crypto/signers 2.5.1). `connect`/`keyStores`/`utils` API compatible with v6 for our use (sign tx as account + key). Sign-as-vault = `Near` connection with accountId = vault + KeyStore containing the agent's private key. No v6→v7 breaking change for connect/signTransaction path; SDK wraps in AgentVaultClient anyway.
- V8 (1-Click API): Base https://1click.chaindefuser.com, OpenAPI v0.1.10. POST /v0/quote fields (required): dry, swapType (EXACT_INPUT|EXACT_OUTPUT|FLEX_INPUT|ANY_INPUT), slippageTolerance, originAsset, depositType, destinationAsset, amount, refundTo, refundType, recipient, recipientType (DESTINATION_CHAIN|INTENTS|CONFIDENTIAL_INTENTS), deadline (ISO). Response includes depositAddress (non-dry), signature/timestamp (verify via `@defuse-protocol/one-click-sdk-typescript` ≥0.1.24). Status: GET /v0/status?depositAddress=[&depositMemo] → {status: PENDING_DEPOSIT|KNOWN_DEPOSIT_TX|INCOMPLETE_DEPOSIT|PROCESSING|SUCCESS|REFUNDED|FAILED, swapDetails, ...}. Optional POST /v0/deposit/submit {depositAddress, txHash}. Auth X-API-Key or Authorization: Bearer.
- V9 (asset ids / storage): Token list GET https://1click.chaindefuser.com/v0/tokens — assetId format `nep141:<contract>` (NEAR origin) for NEP-141, e.g. `nep141:wrap.near`; `chain_deposit_addresses`/deposit addresses depend on origin. For our executor the vault sends exact `amount` via `execute_crosschain`; executor pre-registers storage on the deposit address if the origin FT requires it (check token's storageDeposit logic — spec note [VERIFY] resolves to: NEAR-origin deposits go to a NEAR account address, so `ft_transfer` + prior `storage_deposit` if deposit address is fresh; handled in Phase 7 executor + mocked tests). Contract only transfers once per approved request (idempotent guard).
- V10 (mainnet only): Confirmed — docs state "There is no testnet version of NEAR Intents — use small amounts for test swaps" and HACKATHON.md Q-007 (mainnet, separate dev accounts, tiny amounts, dry:true quotes). Testnet vault for harness; mainnet vault for Intents (Gate 7 human-confirmed).
- V11 (RPC): Public testnet https://rpc.testnet.near.org verified live 2026-11-08 (protocol 88). Mainnet providers per docs.near.org/api/rpc/providers (e.g. https://rpc.mainnet.fastnear.com, https://free.rpc.fastnear.com, archival https://archival-rpc.mainnet.near.org). Indexer default poll 2500 ms with backoff; env NEAR_RPC_URL overrides.
- V12 (global contracts): Available — near-sdk 5.30 has `deploy_global_contract(_by_account_id)` / `use_global_contract` (Promise methods + `near-global-contracts`). P1 only per spec; fallback plain DeployContract ships first.
